# การสำรองและกู้คืนข้อมูล

เอกสารที่ออกเลขทะเบียนไปแล้ว **ออกเลขซ้ำไม่ได้** ตาม §6.4 ข้อมูลที่หายจึงกู้ด้วยการทำงานใหม่
ไม่ได้เลย · หน้านี้คือสิ่งที่ต้องทำให้ครบเพื่อไม่ให้ถึงวันนั้น

## สรุปสั้น

| สิ่งที่ต้องทำ | ความถี่ | คำสั่ง |
|---|---|---|
| สำรองข้อมูล | ทุกวัน (cron ตี 2) | `./scripts/backup.sh` |
| **ซ้อมกู้คืนจริง** | ทุกไตรมาส | `./scripts/restore.sh <ชุด>` ลงฐานทดสอบ |
| ตรวจว่ากุญแจยังใช้ได้ | ทุกไตรมาส | เปิดไฟล์แนบเอกสารลับจากชุดที่กู้มา |
| ย้ายสำเนาออกนอกเครื่อง | ทุกวัน | rsync/rclone ไปเครื่องหรือที่เก็บอื่น |

## สิ่งที่อยู่ในชุด backup หนึ่งชุด

```
backups/20260826-140000/
├── database.dump        pg_dump รูปแบบ custom (บีบอัดในตัว)
├── attachments.tar.gz   ไฟล์แนบทั้งต้นไม้จาก STORAGE_ROOT
├── manifest.txt         เวลา · migration ล่าสุด · git commit · วิธี dump · เวอร์ชัน · จำนวนไฟล์
└── SHA256SUMS           checksum ไว้พิสูจน์ว่าไฟล์ไม่เน่าระหว่างเก็บ
```

## ⚠️ กุญแจเข้ารหัสไม่ได้อยู่ใน backup

ไฟล์แนบของเอกสารชั้นความลับ 1–3 ถูกเข้ารหัสด้วย DEK ต่อไฟล์ ซึ่ง wrap ด้วย `FILE_MASTER_KEY`
(ดู §21.4 ใน `progress.md`) · **กุญแจตัวนี้ไม่ถูกใส่ลงชุด backup โดยตั้งใจ**

- ถ้าใส่ไว้ด้วยกัน ใครได้ไฟล์ backup ไปก็เปิดอ่านเอกสารลับได้ทันที — การเข้ารหัสจะไร้ความหมาย
- **แต่แปลว่าถ้าทำกุญแจหาย ไฟล์แนบชั้นความลับใน backup จะเปิดไม่ได้ตลอดกาล** ไม่มีทางกู้

**สิ่งที่ต้องทำ**

1. เก็บ `FILE_MASTER_KEY` ไว้คนละที่กับ backup — ตู้เซฟ · ซองปิดผนึกของผู้บริหาร · password manager ขององค์กร
2. เก็บ**ทุกรุ่นของกุญแจ** ไม่ใช่เฉพาะรุ่นล่าสุด · ไฟล์เก่าถูก wrap ด้วยกุญแจรุ่นเก่า
   (รูปแบบ `FILE_MASTER_KEY="2:<ใหม่>,1:<เดิม>"`)
3. ทุกไตรมาสให้เปิดไฟล์แนบของเอกสารลับจากชุดที่กู้คืนมาจริง ๆ หนึ่งฉบับ เพื่อพิสูจน์ว่ากุญแจที่เก็บไว้ยังใช้ได้

## ตั้งให้ทำงานอัตโนมัติ

```bash
# /etc/cron.d/esaraban-backup
0 2 * * *  esaraban  cd /srv/esaraban && BACKUP_DIR=/mnt/backup ./scripts/backup.sh >> /var/log/esaraban-backup.log 2>&1
```

ตัวแปรที่ปรับได้

| ตัวแปร | ค่าปริยาย | ความหมาย |
|---|---|---|
| `BACKUP_DIR` | `./backups` | ที่เก็บชุด backup |
| `BACKUP_KEEP` | `14` | เก็บย้อนหลังกี่ชุด (ลบชุดเก่าหลังชุดใหม่สำเร็จแล้วเท่านั้น) |
| `BACKUP_USE_DOCKER` | `auto` | `1` บังคับใช้ container · `0` บังคับใช้ pg_dump ในเครื่อง |
| `COMPOSE_DB_SERVICE` | `postgres` | ชื่อ service ของฐานข้อมูลใน compose |

**⚠️ backup ที่เขียนลงดิสก์ก้อนเดียวกับฐานข้อมูลไม่ใช่ backup** — ดิสก์เสียคือหายพร้อมกันทั้งคู่
ต้องมีสำเนาอยู่คนละเครื่องหรือคนละที่อย่างน้อยหนึ่งชุดเสมอ

## กู้คืน

```bash
./scripts/restore.sh backups/20260826-140000
```

สคริปต์จะตรวจ checksum ก่อน แล้วบังคับให้พิมพ์ชื่อฐานข้อมูลปลายทางยืนยันด้วยมือ
เพราะคำสั่งนี้เขียนทับข้อมูลทั้งหมดในฐานปลายทาง

หลังกู้คืนต้องตรวจสามอย่างก่อนเปิดให้ผู้ใช้เข้า

1. เปิดหน้าทะเบียนแล้วเทียบเลขล่าสุดกับที่ควรจะเป็น
2. เปิดไฟล์แนบของเอกสารชั้นความลับสักฉบับ — เปิดไม่ได้แปลว่ากุญแจไม่ตรง
3. `pnpm db:deploy` เผื่อชุด backup เก่ากว่า migration ล่าสุดในโค้ด

## ซ้อมกู้คืนทุกไตรมาส

**backup ที่ไม่เคยถูกกู้คืนคือความอุ่นใจปลอม ๆ** ทำตามนี้ทุกไตรมาสแล้วบันทึกผลไว้

```bash
# 1. สร้างฐานทดสอบแยก ห้ามกู้ทับฐานจริงเด็ดขาด
createdb esaraban_drill

# 2. กู้ลงฐานนั้น
POSTGRES_DB=esaraban_drill ./scripts/restore.sh backups/<ชุดล่าสุด>

# 3. เทียบจำนวนแถวกับฐานจริง
psql -d esaraban_drill -c "SELECT count(*) FROM documents"
psql -d esaraban_drill -c "SELECT count(*) = max(seq) - min(seq) + 1 AS chain_ok FROM audit_logs"

# 4. ลบฐานทดสอบทิ้ง
dropdb esaraban_drill
```

รายการที่ต้องผ่านให้ครบ

- [ ] จำนวนเอกสาร · หน่วยงาน · ผู้ใช้ ตรงกับฐานจริง
- [ ] ลำดับ `seq` ของ audit log ต่อเนื่องไม่ขาดช่วง
- [ ] index ของ pg_trgm ยังอยู่ (`SELECT * FROM pg_indexes WHERE indexname LIKE '%trgm%'`)
- [ ] เปิดไฟล์แนบเอกสารชั้นความลับได้ด้วยกุญแจที่เก็บไว้
- [ ] จดวันที่ซ้อมและผลไว้ในบันทึกของผู้ดูแลระบบ

## ⚠️ กับดักที่เจอมาแล้วจริง

**เวอร์ชัน pg_dump ต้องไม่ใหม่กว่า server** — `pg_dump` รุ่นใหม่เขียนไฟล์รูปแบบใหม่ที่
`pg_restore` รุ่นของ server เองอ่านไม่ออก (`unsupported version in file header`)
backup จะดู "สำเร็จ" ทุกวันจนถึงวันที่ต้องกู้จริงถึงเพิ่งรู้ · สคริปต์ตรวจให้แล้วและจะหยุดทันที
พร้อมบอกว่าให้ใช้เวอร์ชันไหน

**เครื่องที่มี Postgres สองตัว** — เครื่อง dev อาจมีทั้ง Postgres ที่ติดตั้งบนเครื่องและตัวที่รันใน
Docker ซึ่งแย่งพอร์ต 5432 กัน · สคริปต์เลือกเส้นทางเดียวกันทั้ง backup และ restore เสมอ
(ตัวแปร `BACKUP_USE_DOCKER`) เพื่อไม่ให้ dump ด้วยตัวหนึ่งแล้วไปกู้ด้วยอีกตัว

**ชุดที่ทำค้างไว้ครึ่งใบ** — ถ้าสคริปต์พังกลางคัน โฟลเดอร์ของรอบนั้นจะถูกลบทิ้งทันที
เพราะ backup ครึ่งใบอันตรายกว่าไม่มี backup — คนเห็นโฟลเดอร์แล้วเชื่อว่ามีของ

## ที่ยังไม่ได้ทำ (ตั้งใจ)

| เรื่อง | เหตุผล |
|---|---|
| **WAL archiving / PITR** | ต้องตั้งค่าที่ตัว PostgreSQL และมีที่เก็บ WAL ต่อเนื่อง เกินขอบเขตของสคริปต์ · ตอนนี้จุดกู้คืนที่ดีที่สุดคือ backup รอบล่าสุด แปลว่าอาจเสียงานได้ถึงหนึ่งวัน |
| **ส่งสำเนาออกนอกเครื่องอัตโนมัติ** | ขึ้นกับว่าองค์กรมีที่เก็บอะไร (NAS · เครื่องสำรอง · cloud) ต้องต่อ rsync/rclone เองตามของจริง |
| **เข้ารหัสตัวไฟล์ backup** | ไฟล์แนบชั้นความลับเข้ารหัสมาแล้วในตัว แต่ **ฐานข้อมูลไม่ได้เข้ารหัส** — ชื่อเรื่องของเอกสารลับอยู่ในนั้น ถ้าจะเก็บ backup นอกองค์กรต้องเข้ารหัสไฟล์ก่อนส่งออก |
